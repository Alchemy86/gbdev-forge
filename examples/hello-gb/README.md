# hello-gb

The smallest real example in this repo: one hand-drawn PNG, run through
`forge-png2tile`, assembled (in principle -- see "What's actually verified"
below) into a tiny ROM that shows two tiles on screen.

## Files

- `smiley.png` -- hand-drawn 16x16 PNG (two 8x8 tiles side by side), using
  exactly 4 shades of gray so it auto-quantizes cleanly to the DMG's 2-bit
  palette with no `--palette` file needed.
- `smiley.2bpp`, `smiley_tiles.asm`, `smiley.map.json` -- real output of
  `forge-png2tile`, generated by actually running the tool (not hand-written):
  ```
  cargo run -p forge-png2tile -- examples/hello-gb/smiley.png \
    --out-2bpp examples/hello-gb/smiley.2bpp \
    --out-asm examples/hello-gb/smiley_tiles.asm \
    --out-map examples/hello-gb/smiley.map.json \
    --name smiley_tiles
  ```
  The tool's flip-aware dedup collapsed the 4 source tiles to 2 unique ones
  (the smiley's left/right halves are horizontal mirrors of each other) --
  `smiley.map.json` records exactly which source tile maps to which unique
  tile and flip bit. See `forge_core::dedup_tiles`'s module docs for the
  mechanics (`crates/forge-core`), and this repo's `AGENTS.md` for why flip
  reuse applies to sprites, not DMG backgrounds, in general -- this example
  still uses the tiles as background tiles for simplicity, so the flip
  information in the map isn't applied in `hello.asm` (both unique tiles are
  copied as-is into VRAM and referenced directly).
- `hello.asm` -- a minimal hand-written RGBDS program: waits for VBlank,
  copies the two tiles to VRAM, writes a 2-tile background map, sets the
  palette, and turns the LCD on.

## What's actually verified

This sandbox did not have RGBDS preinstalled, but this repo's own `AGENTS.md`
documents how to fetch a prebuilt release with no package manager -- that was
done here, and the full pipeline was actually run, not just written:

- `smiley.png` -> `smiley.2bpp`/`smiley_tiles.asm`/`smiley.map.json`: real
  `forge-png2tile` output (the command above was actually run).
- `hello.asm` -> `hello.gb`: actually assembled, linked, and fixed with a
  real RGBDS v1.0.4 (`rgbasm`/`rgblink`/`rgbfix -v -p 0xFF`), producing a
  real 32 KiB ROM.
- `hello.gb` actually booted and rendering correctly: verified headlessly
  through the same embedded `terminalgb` core the IDE uses (`cargo run -p
  forge-ide --example run_rom -- examples/hello-gb/hello.gb 10
  /tmp/hello.png`) -- the CPU reaches its `jp`-to-self hang loop by frame 2
  with `LCDC=$91`/`BGP=$E4` and the smiley tile bytes correctly sitting in
  VRAM at `$8000` and the tilemap at `$9800`, and by frame 4 the rendered
  frame buffer shows all 4 DMG shades (white/light/dark/black) in the
  expected repeating smiley pattern (frames 0-3 are still mid-transition,
  same as real hardware taking a frame or two after `LCDC` turns on before
  the first fully-scanned-out frame). **One real bug was caught and fixed
  this way**: the first build left LCDC bit 4 (BG tile data select) unset,
  so the PPU read tile data from the signed-addressing region ($8800-$97FF,
  base $9000) while the tiles were copied to $8000 -- the screen rendered
  solid white until `LCDCF_BG8000` was added to the final `LD A,
  LCDCF_ON|LCDCF_BG8000|LCDCF_BGON`. This is exactly the kind of bug the
  bundled example is meant to be a quick, real sanity check against.
  A second, smaller authentic detail is visible in the render: `hello.asm`
  only overwrites the tilemap's first two bytes, so a couple of leftover
  tilemap cells from the DMG boot ROM's Nintendo-logo scroll (which the real
  boot ROM never clears -- it only scrolls the logo off-screen) still show
  through elsewhere in the background. That is correct, authentic DMG boot
  behavior being modeled accurately, not a bug -- real homebrew has to clear
  VRAM/the tilemap itself for exactly this reason, and this example
  deliberately doesn't, to stay minimal.
- Not yet checked: this exact ROM has not been booted in a real Game Boy
  Doctor/BGB/hardware cross-check, only the embedded `terminalgb` core above.

## To rebuild it yourself (needs RGBDS)

RGBDS isn't vendored in this repo. Fetch a release per this repo's
`AGENTS.md` (`rgbds-linux-x86_64.tar.xz` from
`https://github.com/gbdev/rgbds/releases/latest`, no build step needed), then:

```sh
cd examples/hello-gb
rgbasm -o hello.o hello.asm
rgblink -o hello.gb hello.o
rgbfix -v -p 0xFF hello.gb   # -v fixes the logo + both header checksums
```

Then load `hello.gb` in the IDE (`cargo run -p forge-ide`, "Load ROM", pick
`hello.gb`) or any Game Boy emulator -- it renders the repeating two-tile
smiley pattern described above, not a single isolated smiley (see the
comment in `hello.asm` on why).

## Opening this in the IDE today

Without RGBDS, there's still something real to open:

- `cargo run -p forge-ide`, switch to the **PNG->Tile** panel, and point it at
  `examples/hello-gb/smiley.png` to re-run the same conversion live and see
  its output text in the IDE itself.
- `hello.asm` and `smiley_tiles.asm` are plain text -- open either in the
  **Editor** panel to read/edit them.
- The bundled `gbselftest.gb` test ROM (**Load bundled test ROM**) is this
  repo's one actually-runnable-today ROM for exercising the emulator,
  disassembly, breakpoints, and memory/watch panels end to end.
